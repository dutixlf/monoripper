title: SIGTERM is ignored during PID-1 worker startup

## Reproduction

A real rootless container runs the built CLI as PID 1. A mounted test context pauses after
opening a resource and writing its startup marker. Stop the container before gateway readiness.
RED: Podman needs SIGKILL after its five-second grace period. Exit code is 137 instead of 0.

## Root cause and fix

The CLI registered signal handlers only after `await serve()`. PID 1 ignored SIGTERM during
initialization, so the controller never cancelled the pending worker start.

Register handlers before config/startup. Pass a programmatic-only `startupSignal` to serve.
Cancellation withdraws startup, closes workers/resources and releases the controller writer lock.
The signal only covers startup; callers use Runtime.stop after serve resolves.
Do not convert cleanup failure into successful cancellation. Preserve the cleanup error instead.
No config-file signal option or remote control exposure was added.

## Verification

`bun test tests/e2e/startup-cancellation.test.ts` covers pre-abort, blocked startup, cleanup failure,
writer reacquisition, child termination, and CLI SIGTERM before readiness.
`bun tests/container/startup.ts` proves the PID-1 scenario on the built image.
GREEN: exit 0, context/resource cleanup events, and no listening event.
Arbitrary blocking config module code and stalled kernel filesystem calls are not cancellable promises.
